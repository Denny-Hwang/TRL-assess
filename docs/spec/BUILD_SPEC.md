# PART A — MASTER PROMPT

Deliver a production-quality v1.0.0 through Phases 0–9. Deliverables:

- Tier 1 "Quick Estimate": short, high-level questions producing an approximate TRL.
- Tier 2 "Evidence-Based Assessment": decompose the system into Critical Technology Elements
  (CTEs), assess detailed criteria per TRL, attach or link proof (documents, test data, code
  repositories with commit SHA, DOIs, URLs).
- Excel (.xlsx) export for both tiers; the Tier 2 workbook includes evidence placeholders.
- An optional evidence package (.zip): workbook, JSON, evidence files, SHA-256 manifest.
- A thorough README, in-app Guide pages, contributor documentation.
- Deployment to GitHub Pages via GitHub Actions.

## Non-negotiable principles

1. **Client-side only.** No backend, no analytics, no telemetry, no third-party network calls at
   runtime. Evidence files never leave the browser except inside files the user downloads.
2. **No fabricated criteria.** Every criterion carries a `source` (document id, section, page) and
   an `origin` of `verbatim` | `adapted` | `tailored`. `verbatim` is allowed only for U.S.
   Government public-domain documents (DOE, GAO, DoD, EERE). Never copy ISO text; ISO may be cited
   by clause number only. `tailored` items must include a `rationale`. If a source cannot be
   accessed, STOP and ask the user.
3. **Conservative scoring.** Implement exactly the rules in Part D-2. "Unsure" never counts as
   "Yes". A TRL level requires all lower levels to be achieved. No weighting or heuristics beyond
   the spec.
4. **Honest labelling.** Tier 1 results are labelled "Estimate — self-reported, no evidence".
   Tier 2 results are labelled "Evidence-backed self-assessment — not an independent TRA". The
   disclaimer appears on the Results pages and in every export.
5. **Centralised configuration.** All tunables in `src/config/app.config.ts`; framework content in
   `src/data/frameworks/**`; guide text in `src/content/guide/*.md`. Nothing hard-coded elsewhere.
6. **Sensitive-data safety.** Evidence marked "Sensitive — reference only" must not accept file
   blobs. The UI warns users not to enter controlled information.
7. **Quality gate.** `npm run verify` (lint + typecheck + unit tests + criteria validation + build)
   passes before every PR. Never skip, delete or weaken tests to make CI pass.
8. **Small, traceable changes.** Conventional Commits; one PR per phase; squash-merge; update
   `CHANGELOG.md` `[Unreleased]` and `docs/PROGRESS.md` every phase.

## Tech stack

Vite + React + TypeScript (strict), React Router with HashRouter, Tailwind CSS, zustand +
localStorage (session JSON only), IndexedDB via idb-keyval (evidence blobs), zod, ExcelJS
(lazy-loaded), JSZip, Web Crypto SHA-256, react-markdown + remark-gfm, Vitest + Testing Library,
Playwright, ESLint + Prettier, GitHub Actions. Deviations require an ADR in `docs/adr/`.

## Git workflow (every phase)

Branch per phase, small Conventional Commits, `npm run verify`, update CHANGELOG / PROGRESS /
CLAUDE.md, push, open a PR with the acceptance checklist, watch CI, squash-merge, confirm the Pages
deploy, report to the user. **Fallback** when no remote PR flow is available: merge locally with
`git merge --no-ff` and record the fallback in `docs/PROGRESS.md`.

## STOP conditions

- A framework source document cannot be downloaded or read.
- PROJECT CONFIG placeholders block the step.
- A LICENSE decision is needed.
- CI still fails after 3 fix attempts.
- A requirement would need a backend, network call, analytics or a third-party service.
- Any change to scoring rules (D-2) or Excel structure (D-3) beyond this spec.
- The GitHub repo/owner does not match PROJECT CONFIG.

## Definition of Done (per phase)

Acceptance criteria met and listed in the PR; `npm run verify` green locally and in CI; docs
updated; no TODO without a linked issue; merged; Pages deploy green.

## D-1. Data model

```ts
type Origin = "verbatim" | "adapted" | "tailored";
type TrlLevel = 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9;

interface SourceRef { sourceId: string; section?: string; page?: string; clause?: string }

interface Framework {
  id: string; name: string; version: string; description: string;
  sources: string[];            // ids in SOURCES.md
  disclaimer: string;
  extends?: string;             // e.g., marine-energy-eere extends doe-g413-3-4a
}

interface Tier1Question {
  id: string;                   // e.g., "MEE-T1-L6"
  level: TrlLevel;
  text: string;
  helpText?: string;
  source: SourceRef; origin: Origin; rationale?: string;
}

interface Tier2Criterion {
  id: string;                   // e.g., "DOE-T2-L4-03"
  level: TrlLevel;
  text: string;
  guidance?: string;
  category?: string;            // e.g., technical, program, manufacturing (as in source)
  appliesTo?: ("hardware" | "software" | "process")[];
  mandatory: boolean;
  mandatoryBasis?: string;
  evidenceHints?: EvidenceType[];
  source: SourceRef; origin: Origin; rationale?: string;
  refId?: string;               // reference to a criterion in an extended framework
}

type EvidenceType =
  | "Document" | "Test data" | "Code repository" | "Drawing/CAD" | "Photo/Video"
  | "Publication (DOI)" | "Web link" | "Other";

type Marking = "Public" | "Internal (unrestricted)" | "Sensitive — reference only";
type Verification = "Unverified" | "Verified" | "Rejected";

interface EvidenceItem {
  id: string;                   // EV-0001
  type: EvidenceType;
  title: string; description?: string;
  date?: string; owner?: string;
  url?: string;                 // http/https only
  repoUrl?: string; commitSha?: string; repoPath?: string; tag?: string;
  doi?: string; citation?: string;
  file?: { name: string; sizeBytes: number; sha256: string; mime?: string; blobKey: string };
  marking: Marking;
  verification: Verification; verifiedBy?: string; verifiedDate?: string;
  linkedCriteria: { cteId: string; criterionId: string }[];
}

type CriterionStatus = "Met" | "Partially met" | "Not met" | "N/A" | "Not assessed";

interface CriterionAssessment {
  cteId: string; criterionId: string;
  status: CriterionStatus;
  justification?: string;       // required when status === "N/A"
  note?: string;
  additionalEvidencePlaceholder?: string;
}

interface Cte {
  id: string;                   // CTE-01
  name: string; description?: string; whyCritical?: string;
  critical: boolean; targetTrl?: TrlLevel; owner?: string;
  kind?: "hardware" | "software" | "process";
}

interface Tier1Answers {
  context: {
    projectName: string; technologyName: string;
    assessorName: string; assessorRole?: string; organization?: string;
    oneLineDescription?: string;
    highestFidelityTest?: string; testLocation?: string; testDate?: string;
    environment: "E0" | "E1" | "E2" | "E3" | "E4";
    build: "B0" | "B1" | "B2" | "B3" | "B4" | "B5";
  };
  answers: Record<string, { value: "Yes" | "No" | "Unsure"; note?: string }>;
}

interface AssessmentSession {
  schemaVersion: number;
  appVersion: string; gitSha: string;
  frameworkId: string; frameworkVersion: string;
  createdAt: string; updatedAt: string;   // ISO 8601 UTC
  tier1?: Tier1Answers;
  tier2?: {
    ctes: Cte[];
    assessments: CriterionAssessment[];
    evidence: EvidenceItem[];
    gapActions: {
      cteId: string; nextLevel: TrlLevel; criterionId?: string;
      action: string; owner?: string; dueDate?: string;
    }[];
  };
}
```

## D-2. Scoring rules (each rule needs a named test)

### D-2.1 Tier 1 — Quick Estimate

`Yes(L)` is true when the answer to the level-L question is "Yes". "No" and "Unsure" are both
not-Yes.

| Rule | Definition |
|---|---|
| R1-1 First-yes TRL | Scan L = 9 → 1. The result is the first L with Yes(L). If none, the result is 0, displayed as "< TRL 1". |
| R1-2 Contiguous TRL (headline) | The largest L such that Yes(k) holds for every k ≤ L. If Yes(1) is false, the result is 0. |
| R1-3 Gap flag | Raise if first-yes > contiguous. Message: "Higher level claimed while a lower level is not confirmed." List the missing levels. |
| R1-4 Unsure flag | Raise if any answer at or below the first-yes level is "Unsure". |
| R1-5 Matrix TRL | Look up `tier1-matrix.json[build][environment]`. |
| R1-6 Consistency rating | **High:** no gap flag, no Unsure ≤ first-yes, and \|contiguous − matrix\| ≤ 1. **Low:** \|contiguous − matrix\| ≥ 3, or a gap flag with ≥ 2 missing levels. **Medium:** otherwise. |
| R1-7 Label | Always "Estimate — self-reported, no evidence". The consistency rating describes internal consistency only, not accuracy. |

**Tier 1 heuristic matrix** (tailored, editable; not a standard)

| Build \ Environment | E0 analysis only | E1 laboratory | E2 relevant / simulated | E3 operational, limited | E4 operational, full mission range |
|---|---|---|---|---|---|
| B0 Concept / analysis only | 2 | 2 | 2 | 2 | 2 |
| B1 Breadboard / immature proof-of-concept | 2 | 3 | 3 | 3 | 3 |
| B2 Component prototype (alpha/beta) | 3 | 4 | 5 | 5 | 5 |
| B3 System prototype, partially integrated | 3 | 4 | 6 | 6 | 6 |
| B4 Near-production-quality system prototype | 3 | 4 | 6 | 7 | 7 |
| B5 Final-form system (qualified) | 3 | 4 | 6 | 8 | 9 |

### D-2.2 Tier 2 — Evidence-Based Assessment

| Rule | Definition |
|---|---|
| R2-1 Applicable | A criterion is applicable to a CTE if `appliesTo` is absent or includes `cte.kind`. |
| R2-2 Satisfied | Satisfied if (a) status = "Met" AND ≥ 1 linked evidence item with verification ≠ "Rejected"; OR (b) status = "N/A" AND the justification is non-empty. "Partially met", "Not met" and "Not assessed" are never satisfied. |
| R2-3 Evidence requirement | For mandatory criteria, R2-2(a) is required: "Met" without evidence is not satisfied. Optional criteria marked "Met" without evidence also do not count toward completeness, but raise a warning only. |
| R2-4 Level achieved | Level L is achieved if every applicable mandatory criterion at L is satisfied AND level L−1 is achieved (level 0 counts as achieved). If level L has zero applicable mandatory criteria, it is achieved only if ≥ 1 applicable criterion at L is satisfied; otherwise the level is flagged "No mandatory criteria — needs assessor confirmation" and treated as not achieved. |
| R2-5 CTE TRL | The highest achieved level. 0 means "< TRL 1". |
| R2-6 Next-level completeness | At level CTE TRL + 1: (satisfied applicable criteria) / (applicable criteria excluding N/A), as a percentage. |
| R2-7 System summary | The minimum CTE TRL over CTEs with `critical = true`; report the limiting CTE id(s). With no critical CTEs, show "Not computed — mark at least one CTE as critical". Label: "Conservative summary (minimum of critical CTEs). This is a reporting convention, not a mandated formula." |
| R2-8 Evidence coverage | Per CTE: (Met criteria with ≥ 1 non-rejected evidence) / (Met criteria). |
| R2-9 Tier delta | Tier 2 system summary minus Tier 1 contiguous TRL; explain when \|delta\| ≥ 2. |
| R2-10 Label | Always "Evidence-backed self-assessment — not an independent Technology Readiness Assessment". |

Evidence type is never weighted. Verification status matters only through the "Rejected" exclusion.

### D-2.3 ARL — Adoption Readiness Level (added 2026-09-24, ADR-0005)

Source: DOE Office of Technology Commercialization, _Adoption Readiness Assessment_, Version: April
2025 (`doe-otc-arl-2025`). The ARL is independent of every TRL rule above and is never combined with
a TRL.

| Rule | Definition |
|---|---|
| R3-1 Rating | Each of the 17 dimensions is rated Low, Medium or High risk against the rubric text, or N/A (source, p. 2); the tool adds "Unsure" and the initial "Not assessed". |
| R3-2 Conservative count | "Unsure", "Not assessed", and "N/A" with an empty rationale count as **High**. "N/A" with a rationale is not counted. Each case is listed in a flag. |
| R3-3 ARL | Tally the dimensions counted Medium and High; ARL = look-up table (source, p. 13), rows = Medium count, columns = High count, counts ≥ 8 in the "8+" row/column. The table is used unmodified. Band: 1–3 Low Readiness, 4–6 Medium Readiness, 7–9 High Readiness. |
| R3-4 Start / End | ARL Start from the current ratings. ARL End from the targets; a dimension without a target keeps its current rating. |
| R3-5 Profile | Per core risk area, the count of dimensions counted Low / Medium / High / N/A. Descriptive only. |
| R3-6 Warnings | A Low/Medium/High rating without a rationale, and a target that lowers a risk without a planned action, raise warnings; neither changes the number. |
| R3-7 Labels | Result: "Adoption readiness self-assessment — not reviewed or endorsed by DOE". Target: "Target — planned, not achieved". The ARL disclaimer appears on the result page and in the workbook. |

### D-2.4 Call-profile checks (added 2026-09-24, ADR-0005)

| Rule | Definition |
|---|---|
| R4-1 TRL Start | The Tier 2 system summary when it is computed; otherwise the Tier 1 contiguous TRL when Tier 1 has answers; otherwise "not evaluated". Shown with that tier's label. |
| R4-2 Applicability | A check with `topics` applies only when one of those topics is selected. |
| R4-3 Results | Pass / Fail (severity `fail`) / Warning (severity `warning`) / Info / Not evaluated (input missing). Every result lists the requirement sentences it tests, quoted, with pages. |
| R4-4 CLIMR FY26–27 | `trl-start-min` 4 (fail); NE: `trl-start-min` 5 (warning); `trl-end-range` 4–9; `arl-start-range` 1–9; `arl-end-range` 2–9; `arl-increase` (all fail); NE: `no-high-risk-in-area` D (warning); `trl-definitions` (info). Source `doe-tcf-climr-fy2627`, pp. 12–13, 37, 46, 49, 54, 65. |

The checks read the call's words; they never decide eligibility, and they never change a rating or a
score.

## D-3. Excel workbook specification

**D-3.0 Common**

- File name: `TRL_<Tier1|Tier2>_<project-slug>_<YYYYMMDD-HHmm>.xlsx` (local time), `.zip` for packages.
- Every sheet: bold header row, freeze panes below the header, autofilter, sensible column widths,
  wrap text on long-text columns.
- Every workbook starts with a **README** sheet: purpose, how to read each sheet, how to fill
  placeholders, the disclaimer, tool version, framework id/version, git SHA, generation timestamp (UTC).
- Status cells use data validation lists plus conditional formatting; colour is never the only
  signal — the text value is always present.
- All user-entered text is written with the formula-injection guard.
- Computed values are static at export time. README states: "Edits in this workbook do not
  recompute the TRL; re-import JSON into the app to recompute."

**D-3.1 Tier 1 workbook** (sheet order)

1. **README**
2. **Summary** — project, technology, assessor, organization, date; contiguous TRL (headline),
   first-yes TRL, matrix TRL, consistency rating, flags; label and disclaimer.
3. **Context** — `Field | Value`; all context fields, environment and build codes with descriptions.
4. **Responses** — `TRL | Question ID | Question | Answer (validation Yes/No/Unsure) | Note | Origin | Source`.
5. **Next_Evidence_Placeholders** — for levels contiguous+1..contiguous+2 (capped at 9), the Tier 2
   criteria titles. Columns `TRL | Criterion ID | Criterion | Planned evidence (placeholder) |
   Evidence link / path (placeholder) | Open (=IF(F2="","",HYPERLINK(F2,"Open"))) | Owner | Target date`,
   plus 10 blank placeholder rows.
6. **References** — `Source ID | Title | Issuer | Version/Date | URL (hyperlink)`.

**D-3.2 Tier 2 workbook** (sheet order)

1. **README** — includes "How to attach evidence in Excel": (a) URL in "Location / URL";
   (b) relative path in "Local file (relative path)" with the file in `evidence/` next to the
   workbook; (c) the Open column creates a clickable link; (d) never paste sensitive content — use
   "Sensitive — reference only" rows for pointers.
2. **Summary** — system summary and limiting CTE(s); table
   `CTE ID | CTE | Critical | CTE TRL | Target TRL | Next-level completeness % | Evidence coverage %`;
   Tier 1 contiguous TRL and delta; label and disclaimer.
3. **CTE_Register** — `CTE ID | Name | Kind | Critical (Yes/No) | Description | Why critical | Owner |
   Target TRL (1–9 validation) | Assessed TRL`.
4. **Criteria_Assessment** — one row per CTE × applicable criterion:
   `CTE ID | CTE | TRL | Criterion ID | Criterion | Category | Mandatory (Yes/No) | Origin | Source |
   Status (validation) | Justification (N/A) | Satisfied (Yes/No, computed) | Evidence IDs |
   Additional evidence (placeholder) | Assessor note`. Conditional formatting on Status and
   Satisfied; grouped by CTE then TRL.
5. **Evidence_Register** — `Evidence ID | Type (validation) | Title | Description | Linked CTE/Criteria |
   Location / URL (hyperlink) | Local file (relative path) | Open (formula) | Repo URL | Commit SHA |
   Repo path / tag | DOI | File size (bytes) | SHA-256 | Date | Owner / custodian | Marking (validation) |
   Verification (validation) | Verified by | Verified date | Bundled in package (Yes/No)`.
   After the existing rows, append `BLANK_EVIDENCE_PLACEHOLDER_ROWS` rows with ids `EV-P001…`, all
   validations active, the Open formula present, a light fill and a "placeholder" note.
6. **Gap_Actions** — pre-filled with unmet mandatory criteria at each CTE's next level:
   `CTE ID | Next TRL | Criterion ID | Gap description | Planned action | Planned evidence (placeholder) |
   Owner | Due date | Status (Open/In progress/Done)`, plus 20 blank rows.
7. **Review_Signoff** — assessor block (name, role, date, signature placeholder); independent
   reviewer block (name, affiliation, date, conclusion validation Concur / Concur with comments /
   Do not concur, comments, signature placeholder); note that reviewer sign-off is outside the
   tool's scoring.
8. **References** — as in Tier 1.
9. **Metadata** — schemaVersion, appVersion, gitSha, frameworkId, frameworkVersion, createdAt,
   updatedAt, exportedAt, packageType (standalone/zip), counts.

**D-3.3 ARL workbook** (added 2026-09-24, ADR-0005; follows D-3.0; file name
`ARL_<project-slug>_<YYYYMMDD-HHmm>.xlsx`; README note "Edits in this workbook do not recompute the
ARL; re-import JSON into the app to recompute.")

1. **README** — label, ARL disclaimer, how the ARL is calculated, provenance.
2. **Summary** — project, technology, assessor, rubric and version; ARL Start and ARL End (target)
   with bands; the tallies and per-area tallies; flags; with a call profile: profile, topic, the four
   title-page numbers (ARL Start, ARL End, TRL Start with its basis, TRL End) and the check counts;
   label and disclaimer.
3. **Scope** — `Field | Value`: names, technology scope, value chain scope, timeline, policy
   environment, the session's TRL framework.
4. **Risk_Assessment** — one row per dimension: `Core area | Dimension ID | Dimension | Current rating
   (validation) | Counted as | Why counted so | Rationale | Evidence / reference | Target rating (end of
   project) (validation, incl. "Same as current") | Target counted as | Planned action | Low risk
   (rubric) | Medium risk (rubric) | High risk (rubric) | Origin | Source`. Conditional formatting on
   the rating columns.
5. **ARL_Lookup** — the p. 13 table (`Medium \ High`, 0…8+), the Start and Target cells filled and
   carrying a note, the bands and the source.
6. **Call_Checks** — only when a call profile is selected: `Check ID | Check | Result | Value tested |
   Detail | Requirement (quoted) | Source (doc, section, page)`.
7. **References** — the rubric, and the call when a profile is selected.
8. **Metadata** — as D-3.2 item 9, plus the session's TRL framework.

### D-6.1 Tier 1 questions for `marine-energy-eere` (origin "adapted")

| TRL | Question (Yes / No / Unsure) |
|---|---|
| 9 | Has the actual system, in its final form, been operated over the full range of expected mission conditions? |

| 7 | Has a near-production-quality system prototype, at or near full scale and with most functions available, been demonstrated in an operational environment? |
| 6 | Has a system-level (beta) prototype, partially integrated with existing systems, demonstrated engineering feasibility in an environment relevant to the end user? |

### D-6.2 Tailoring items for `marine-energy-eere` (origin "tailored")

| Level | Tailored criterion | Rationale |
|---|---|---|
| ≥ 4 | A risk register and FMECA exist for the element. | The NREL Marine Energy Risk Management Framework requires both at TRL 4 and above for WPTO open-water projects. |
| 5 | The relevant-environment test used conductive seawater (or a justified equivalent) where electrical coupling or corrosion is plausible. | Ocean-specific coupling paths do not appear in air-only tests. |
| 5–6 | Environmental extremes representative of the deployment were tested (temperature/cold, humidity inside the enclosure, immersion/pressure) and recorded. | Arctic/marine deployment conditions. |
| 6 | A pre-deployment test plan distinguishes deck/dockside results from open-water results. | Deck conditions can misrepresent at-sea communication performance. |
| 6–7 | Field duration and failure events are logged with a root-cause status for each failure. | Needed to claim "engineering feasibility fully demonstrated". |
| 7 | The prototype uses production-intended parts for critical functions (no hand-built critical parts without a documented build specification). | Supports "near-production-quality prototype" in the EERE TRL 7 definition. |
| 7–8 | Calibration procedure and data path are documented, and transmitted values match calibrated values. | Data integrity for observing-system use. |
| 8 | Data submission pathway to the intended observing program is established (if applicable). | End-user specification for ocean observing. |

Tailored items stay generic — no real project, device name or data.

## D-9. Sensor development-stage crosswalk (informational only)

| Stage | Development term | Typical TRL | Primary goal |
|---|---|---|---|
| 0 | Concept | 1–2 | Define the sensor opportunity and establish a technically credible development approach. |
| 1 | Component-Level Evaluation | 2–3 | Select key components and understand performance limits, variability and integration risks. |
| 2 | Proof of Concept | 3 | Demonstrate fundamental technical feasibility of the sensor concept. |
| 3 | Breadboard Prototype | 3–4 | Develop and optimize the signal chain, electronics, algorithms, firmware and measurement method. |
| 4 | Board-Level Prototype (PCB) | 4 | Validate custom electronics, PCB layout, noise performance, power consumption, firmware and electrical interfaces. |
| 5 | Integrated Prototype | 5 | Validate end-to-end system functionality and performance in representative operating conditions. |
| 6 | Miniaturized Prototype | 5–6 | Validate target form factor, size, weight, thermal behavior, packaging, usability and performance after miniaturization. |
| 7 | Production-Intent Prototype | 6–7 | Support design validation, reliability, regulatory testing and manufacturing-readiness assessment. |
| 8 | Pilot Production Build | 7–8 | Verify manufacturability, yield, quality, calibration, end-of-line testing, supply-chain readiness and process repeatability. |
| 9 | Technology Transfer / Commercial Licensing | 8–9 | Enable a commercial partner to complete qualification, manufacture, market, sell and support the product. |

Display with the note: "Stage models are organization-specific. Use them for communication, not as
the basis for TRL scoring."
